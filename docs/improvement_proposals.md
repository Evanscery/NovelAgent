## 待审批条目

### IP-001 玩家输入应支持“结构化输入模式”，而非只靠启发式解析
- 背景：S1 只是给启发式解析打补丁（归一化转义、约束 target）。本质上自然语言→意图/目标的抽取永远脆弱。
- 建议：在 RP 输入上增加一个可选的**结构化输入通道**（如 `intent`/`target`/`action`/`dialogue` 显式字段，或一个轻量 DSL），自然语言解析退为兜底。前端可直接产出结构化输入。
- 满足约束：高可配置（输入模式可选）、前端友好（前端给结构化）、高解耦（解析器与兜底分离）。
- 状态：已拒绝（2026-06-18，RP 用户侧保持纯自然语言；显性字段由后端解析并回显，避免把复杂度转移给玩家）

### IP-002 记忆层应尽快从“Markdown 主存”过渡到“结构化主存 + Markdown 投影视图”
- 背景：S2 需要专门清理旧 `summaries.md` / `index.md` 噪声，说明 Markdown 同时承担“真相源 + 展示层”时容易积累历史污点。
- 建议：长期把 memory/index 的 canonical 数据迁到 JSON/SQLite，Markdown 只作为导出视图或审阅副本。
- 满足约束：更高解耦、更好项目间隔离、更利于前端展示与配置页读取。
- 风险：会提高迁移复杂度，因此只建议在中期 M1/M3 稳定后再做。
- 状态：已采纳，第一阶段已落地（2026-06-18）：新增 `memory/scenes.json` 结构化主存，`summaries.md` / `index.md` 保持投影视图兼容旧流程；`normalize-memory` 会从旧 Markdown 生成结构化主存。

### IP-003 Prompt snapshot 应分为“审计视图”和“预算视图”两层
- 背景：M1 第一阶段已经开始把每步 prompt 快照与 trace 落盘；M1 第二阶段又加入了 budget 调度与 section 级 keep / truncate / drop 决策。随着策略增多，单纯保存最终 prompt 不足以解释“为什么某段上下文被保留/截断/降级”。
- 建议：后续 trace 除了记录最终 prompt，还应记录 collector 来源、优先级、调度决策、被丢弃原因，形成“审计视图”；同时另保留一个面向前端/调试页的简化“预算视图”。
- 满足约束：前端友好（调试页可直读）、高解耦（trace 不绑具体 UI）、高可配置（可切换输出粒度）。
- 状态：已拒绝（2026-06-18，原因见处理记录：过度复杂化，用户不应触碰过于核心的后端配置）

### IP-004 compress/summarize 应区分“规则压缩”和“模型压缩”两级通道
- 背景：M1 当前已经接入 deterministic `compress` 策略，用于在不调用 LLM 的情况下压缩 retrieved/stable/memory 类上下文。但这种规则压缩可控、便宜，却不总是语义最优。
- 建议：后续把压缩分为两级：默认走 deterministic 规则压缩；仅在最终验收或高价值场景下，允许受控启用“模型压缩”作为可选通道，并明确写入 trace。
- 满足约束：最小 LLM 调用（默认不走模型）、高可配置（两级可切换）、高解耦（压缩器可插拔）。
- 状态：已拒绝（2026-06-18，原因见处理记录：当前需求下 LLM 压缩已是最佳）

### IP-005 Skill 系统选型：先内置 Python registry，MCP 留作未来外部通道
- 背景：用户提出为 agent（如 GM）提供 skill（掷骰 `1d10`/`1d100` 等），并要求选型“确有必要、确有优势，不为复杂度而复杂度”。
- 调研结论：
  - 掷骰类技能本质是纯函数，用内置 Python registry 实现最小、可 deterministic 测试、零外部依赖；引入 Node.js/JS 运行时仅为一个函数属于过度设计，**确无优势**。
  - MCP 是参考项目（AIRP-MCP-Server）已验证的 tool/resource/prompt 标准，比自造 JS 插件协议更通用。但只有内置确定性技能时接 MCP 属于过度设计，应**预留接口、暂不接入**。
  - 建议：内置 registry 与未来 MCP 通道统一在同一 skill 抽象下，对 agent 暴露同一调用契约。
- 满足约束：最小 LLM 调用（技能默认确定性）、高解耦可插拔、高可配置、避免无谓复杂度。
- 状态：待审批（详见 `next_step_optimization_plan.md` G2）
