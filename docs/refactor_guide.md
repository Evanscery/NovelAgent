# novelAgent

## 系统整体

用户层
|
Runtime层
|
agent层
|
数据层

以轮次(Round)作为agent调度与数据版本管理的最小单位，一个round即为一轮写作，即RP的一回合，或小说的一章。

### 技术栈

前后端解耦，采用RESTful API 沟通。

前端：React + TypeScript + Vite

后端：python + fast api

数据库：不使用数据库，数据以明文方式存储为md文件等

### 依赖解耦与兼容

本项目灵感来自于酒馆sillytavern，但与sillytavern完全解耦，不依赖sillytavern任何功能。在项目中除了兼容层也不应出现sillytavern的字样

但兼容sillytavern的角色卡，允许从sillytavern的角色卡导入项目，允许从sillytavern的预设提取用于agent的skill(文风/jailbreak等)

### 项目目录与配置控制

为每一个小说/RP项目（即对应酒馆sillytavern的一张角色卡）创建独立工程目录，并实现项目配置覆写。

如
workspaces/proj1/config.yaml
workspaces/proj2/config.yaml

proj1应替换为非重复项目id并应由system控制，不交由用户
具体显示名由项目目录下config控制

应允许用户运行时动态切换novel/rp mode，由配置控制，以此解耦并留下未来更多mode的扩展空间

目前已知mode配置的作用：切换前端工作台的显示
（如小说模式是大纲控制，伏笔查看等，RP模式则是玩家行动，世界演化等）
（但不同模式只是默认显示tab不同，这些标签页都可以手动打开）
（底层实现是统一接口）

### 实现约束

应保持工程目录尽可能简洁，避免滥发代码文件，该抽象的类必须抽象为类，如resource，agent

## agent层

agents的核心原则：权责分割，任何agent不应具有自己职责之外的权限。

### agent的构建与skill

每个agent角色（或节点），由类似一个函数模板的方式定义，而不是简单的一段prompt

其在创建时，必须包含以下属性：
属性|描述|访问控制
id|id|数据结构控制与存储，只读，创建时初始化，唯一
name|智能体的名字，如director，memory_recaller|可随时更改
task|智能体的任务，如director的任务是决策与任务分配，是agent的核心|创建时初始化，可编辑
input|告诉智能体它将被提供什么样的输入，包含什么内容|创建时初始化，可编辑（低频）
output|描述智能体输出和格式|创建时初始化，可编辑（低频）
permission|重要参数，实现上下文隔离，每个智能体只能看见自己需要看见的内容|创建时初始化，可编辑（低频）
model|调用哪个模型配置|可为空
skills|可用skills的列表|继承全局（公共skills），可修改，可由调用者动态挂载
tools|可用tools的列表|继承全局（公共tools），可修改，可由调用者动态挂载
head|提示词头部，用于一些特殊提示词结构|继承全局，可为null
tail|提示词尾部，用于一些特殊提示词结构|继承全局，可为null

这些属性硬存储在数据结构中，发送agent请求时，会调用parser将这些参数解析并组合成prompt。

如permission是一个hash<string, vector>，vector对象存放目录名或文件名，如permission['read'] = 'memory'。
prompt里会写：“你只能**读取**以下字段： 'memory'...”
parser维护一层映射：'data/memory'以解耦（若后续更换数据库实现则更新映射即可，甚至可以做到数据库实现在项目间独立，因为每个项目有自己独立的映射）。
若agent call了读取工具，但工具函数体发现出现越权访问，则reject

### agents 与 角色分类

有两种agent，workflow agents与system agents。

workflow agents：由用户在comfy-ui like的画布前端中交互式地创建，通过节点/接线/配置的方式组织成有向无环图。
其中，主agent(director)必备。接线只决定优先级并保证无环，不严格表示执行顺序，不保证每个节点均有数据流过（可被绕过），由主agent决策。 

system agents：独立于workflow，不参与实际创作循环，负责处理用户与系统的交互。
比如“帮我添加一个新的节点，用于……”，“帮我把大纲修改为……”, “读取该预设的文风为skills”

一轮的流程（内置的agents与roles）： 
director：
-决策，任务分配。
-主要工具：call_agent, await ……

recaller/scout：负责召回数据 
writer：文本生成 
brainstormer：提供灵感 
critic/reviewer：对抗式/批判式修改建议 
maintainer：更新/维护数据

### 一轮的结束条件

目标:尽最大努力避免循环

已达到最大迭代次数。
Token 或 Tool Budget 用尽。
所有流程完成，主动调用 Finalize。

### 标准化工具体

不要滥发工具
例如不要出现：

readFile()
readMemory()
readLore()

而统一成：

read(resource)
search(resource)
write(resource)

## 数据层

数据采用项目级独立，每个项目都独立维护自己的数据区，绝不也无权访问其他项目的数据

### 数据流与层级结构

数据流层级结构与系统层级结构相同：
用户层
|
agent层
|
数据层

用户不与数据层直接交互，而是通过agent。

数据召回与数据维护是数据层的核心，是完全独立的两个功能区。
maintainer与recaller，二者互不依赖，也不共享prompt。

### 数据设计

数据以资源(resource)的概念存储，每一种数据是资源的一个实例，包含一个独立的目录。
每个资源应该定义自己的属性，在目录中包含properties.md：
存储方式
召回策略
维护策略
版本策略

至少需要存这些数据实例： 大纲（长期目标）/细纲（短期目标，本回合需发生的事情）/当前状态（可视为上一轮的小总结，截至最新，故事发展到什么阶段，目前各个角色在做什么，处于什么状态）/ 变量（人物的状态，持有什么装备，道具，人物好感度等量化的变量，涉及角色卡的独立前端更新，可以从现存角色卡的变量中拆解得到，可为空） / 世界书（背景设定，人物设定，覆写常识与客观事实） / 客观事实（比如同人作品的设定，现实世界的客观真相等，可以通过搜索工具获取并更新） / 人物记忆（角色隔离，维护角色所知的事实及人际关系等，如a知道b给c写过信，d不知道） / 创作笔记（创作中动态发现的内容，反馈，新的约束）

Data Layer 不主动维护数据，不主动召回数据，也不关心数据的内容。
它只是做：
-存储
-检索（不是数据库search，而是提供接口给agent，如召回agent在阅读分级总结后，发现目前场景主要跟SCE-03回合有关，于是调用工具，召回SCE-03回合的正文全文，然后由agent自行在全文中提取需要用到的相关记忆）
-版本管理（快照，投影，分支，压缩，恢复）
-为agent提供接口
-维护索引（方便agent进行grep/symbol search等方式）

所有"理解数据"都交给 Agent。

数据按照更新频次可分为三类：

1.需要每轮更新的数据：
细纲（当前回合的plan）
当前状态（可视为上一轮次的小summary，辅助本轮创作）
变量

2.不一定每轮，但需要频繁更新的数据：
角色记忆（人际设定，关系）
轮次记忆
伏笔

3.更新频率低的数据：
事实（如：故事中需用到的客观事实，网络搜索结果等）
大纲（一般经过多个轮次才会更新目前所处阶段或续写新大纲）
创作笔记
世界观设定（几乎不在运行时变动，或只增量）

举例：若director发觉上轮才更新过大纲，且剧情发展明显没有进入新的阶段，这轮就选择绕过大纲的maintainer。

数据按长度与数据结构可分为三类：
1.长度很长，可预计一定会超出模型上下文或严重影响模型能力，不能全量塞入请求的数据，如：
-每轮正文

2.长度较短，适合放入请求的数据，如：
-当前状态
-伏笔
-创作笔记
-大纲
-细纲

3.长度较短，但不适合让模型看到的数据，如:
-变量（只应用于前端显示，让用户理解，若发送给ai，易造成创作机械化数字化）
（*除非创作要求如此，比如数据流小说）

### 数据召回

数据召回遵循以下原则：
1. 代码不参与检索，只提供访问能力

框架不负责决定"召回什么"，也不负责"怎么召回"

代码层只负责：
-数据存储
-数据索引
-数据访问
-权限校验

所有检索策略、筛选逻辑、召回内容均由 Recaller Agent 决定。

2. 数据之间不隐式关联

例如：

读取当前状态，不会自动读取角色记忆。

读取角色记忆，也不会自动读取世界书。

任何额外的数据访问，都必须由 Agent 主动请求

3. Recaller 可以递归召回
也就是说，召回可以不是一次性完成，而是可以边思考边读取
读 Summary
    ↓
发现需要第 128 楼
    ↓
读第 128 楼
    ↓
发现提到了一封信
    ↓
搜索 "信" 对应的角色记忆
    ↓
发现涉及世界设定
    ↓
读取相关世界书

**但是**，涉及recaller的调用必须回到director做决策——即recaller没有决策权限，它只有建议权，在上面的例子里，memory recaller发现信与世界设定有关，则它可以在director call它的函数中回调传入"need lore"的信息，由director决策，若director认为，并行发出的lore recaller已找到了这个信息，不需再次call recaller，则可以忽略这个信息，反之也可以递归召回。
即数据召回必须满足agent的权责分割原则

**数据召回的方式**根据上述数据类型的不同，有以下几种：

1.长度很长，更新频率很高的数据（如正文记忆）——多级索引 每轮维护一个summary，将正文归档。需要召回时，summary全量进入上下文。recaller根据summary定位到需要全量召回的正文编号，调用工具召回该轮全文，然后由agent自行定位到需要召回的相关记忆。

2.长度很长，更新频率很低的数据（如世界书等事实）——单级召回 由对应recaller进行检索与召回 

3.长度很短，更新频率很高的数据（如当前状态，变量）——默认注入 
由agent权限控制，parser为需要的agent直接注入（比如writer和critic都能直接看到当前状态，变量，本轮细纲等）。避免recaller一旦出错带来的错误传递 

4.长度很短，更新频率很低的数据（如伏笔，创作笔记等）——按需读入
由agent自行决定是否需要该数据，自行选择是否读入

5.不适合注入的数据（变量等）—— 只维护，不召回
只由maintener维护，不进行召回，运行时数据层把数据发送回前端进行渲染。

### 数据维护

数据维护与数据召回独立，分属不同的agent，不互相依赖，不共用prompt

每一个数据都有唯一对应的一个maintainer

不是所有的maintainer都需要每轮执行，按上面提到的频率分类，每轮更新的，必须每轮维护，其他的，由director决定是否维护

长数据采用增量维护，短数据采用覆盖维护

使用grep / symbol search的read->edit策略，避免长文件的写错误，更新需维护索引，索引格式可不统一

如世界书：
World Lore

├── 魔法

├── 国家

├── 历史

└── 教会

### 版本控制与回滚

1. 以 Turn（楼层）作为最小版本单位

每完成一轮 Workflow，就产生一个新的 Commit（或 Snapshot），对应小说的一章。Commit 记录本轮所有 Agent 对数据层产生的修改，而不是仅保存最终状态。

2. 根据数据不同采用增量更新或覆盖更新两种策略

Maintainer 根据数据长度与类型选择更新策略

3. 所有数据具有版本历史

每个资源（大纲、世界书、角色记忆等）都保留历史版本，可以查看任意时间点的内容，而不是只有最新版本。

4. 当前数据是历史的投影（Projection）

系统维护一份最新状态作为快速访问入口，但它只是历史 Commit 应用后的结果，而不是唯一数据源。真正的数据来源始终是版本历史。

5. 回滚本质是切换版本，而不是删除数据

回滚到第 N 楼时，不删除后续数据，而是将工作区切换到对应 Commit。即回滚默认为创建新的Branch，除非用户明确操作为删除。（提供branch与delete接口）

例如：

Turn 120
    │
Turn 121
    │
Turn 122
    │
回滚到 120
    │
Turn 121'
    │
Turn 122'

这样既支持时间回溯，也支持剧情分支。

6. 数据更新具有原子性

一轮 Workflow 的所有维护操作要么全部提交成功，要么全部取消，不允许出现"正文已经更新，但角色记忆没有更新"的中间状态。整个 Workflow 应作为一次事务（Transaction）提交。但允许部分数据本轮不更新，即输出状态为 NULL（实际为不调用maintainer agent）

7. Agent 永远操作工作区（Working Tree）

Workflow 中所有 Agent 都只读取当前活跃项目的数据。

## 用户层

### 前端技术栈

React + Typescript + Vite

标签页 + 多级导航的方式

风格现代，简洁。**易用性原则**

默认模式下实现傻瓜式的操作，能够流畅完成从配置工作流，模型，导入，项目初始化，到完成X轮的创作或RP的全流程。
默认模式下一切操作需以面向零技术用户的原则开发

专家模式下允许进一步的配置

### 工作流配置
comfyui的画布like的工作流配置器工作台，节点/接线/内部变量配置的方式，实现高可自定义和简单易用性。

允许以json的格式保存与导出

### 配置页

配置集中在一起，包括模型配置，供应商配置……

允许自定义供应商，自定义provider类型，如openAI，openAI response， anthropic……

每个 Agent 都有独立配置：

Name
Task
Model
Skills
Tools
Permission
Input / Output

Workflow 保存的是这些配置，而不是 Prompt。

运行时由 Parser 动态生成 Prompt。

因此：

配置是静态的，Prompt 是动态生成的。

### 数据可视化

前端不仅管理 Workflow，也负责管理 Data Layer。

用户可以查看：

大纲*
世界书
当前状态*
角色记忆
创作笔记
事实
变量

每类数据都有独立编辑器和历史版本查看。
