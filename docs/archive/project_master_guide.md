# NovelAgent 项目总指导文件

## 0. 文档定位

本文档是 NovelAgent 的**总指导文件**。它替代原先的 `audit_and_roadmap.md`，用于统一回答以下问题：

1. **项目到底要实现什么**。
2. **现在已经做到什么程度**。
3. **离“多 Agent 自动小说写作 / RP”目标还差什么**。
4. **每一项设计为什么值得做**。
5. **哪些复杂度是必要的，哪些复杂度不应该引入**。
6. **如何把 SillyTavern / 酒馆角色卡迁移进项目格式**。
7. **前端应该做什么，不应该做什么，以及什么时候进入实现计划**。
8. **如何以最小 token 花费推进开发与测试**。
9. **如何保证高可配置性、高可插拔性、环境隔离、上下文隔离、可恢复与可暂停**。

本文档的总设计原则只有一条：

> **最大程度利用 agent 的能力完成任务，而不是为了“看起来高级”去引入无意义复杂度。**
>
> 只有在某项设计**确实必要、确实能稳定提升效果、效率、可维护性、可迁移性或可运维性**时，才应进入实现计划。

## 1. 项目最终目标

NovelAgent 的最终目标不是“能生成几章小说”，而是实现一套：

```text
玩家可互动
多 Agent 可协作
长篇上下文可维持
设定与记忆可审计
写作成本可控
可迁移酒馆卡
高可配置
高可插拔
环境隔离
上下文隔离
可恢复可暂停
可扩展到 RP / 沙盒 / 长篇连载
```

具体拆成八个核心目标：

### 1.1 自动小说写作

系统应能：

- 自动生成题材设定、角色、世界规则、阶段大纲。
- 按章节稳定推进正文。
- 在多章情况下保持世界观、角色关系、物品状态和伏笔一致。
- 用审查闭环提高质量，而不是盲目堆更大模型。

### 1.2 玩家互动 / RP

系统应能：

- 读取玩家输入。
- 基于当前状态与视角限制生成 GM 旁白或角色回应。
- 支持玩家行动进入状态流转，而不是只在 prompt 中“拼接一句话”。
- 在 RP 模式下保持玩家可见信息与后台真实状态分离。

### 1.3 高效与省 token

系统应能：

- 用尽量短的上下文达成稳定效果。
- 把高模型用在真正值得用的步骤。
- 把快模型用在审查、整理、补写、辅助分析。
- 失败时局部重试，而不是整章 / 整本盲目重跑。
- 用缓存和结构化状态减少重复调用。

### 1.4 写作效果好

系统应能稳定追求：

- 叙事连贯
- 逻辑严密
- 角色不 OOC
- 文风不 AI 八股
- 长章节有完整起承转合
- 网文节奏、钩子、修罗场、爽点等题材卖点能自然落地

### 1.5 可迁移酒馆卡

系统应能把 SillyTavern / 酒馆角色卡里的真正价值迁入：

- 人物设定
- 世界设定
- 规则与触发条件
- 隐藏信息与可见信息边界
- 多 NPC / 多角色关系
- 好感度、任务、经济、时间等可变状态机制

而不是只把卡内容粗暴拷成一个 prompt。

### 1.6 高可配置性

系统应能让以下对象全部配置化，而不是写死在代码里：

- Prompt modules
- Preset
- Profile
- Agent 列表
- Pipeline 顺序
- 模型映射
- 重试 / 超时 / 降级策略
- Recall 预算
- 前端可见配置

### 1.7 高可插拔性

系统应能按模块替换或新增：

- Agent
- Prompt module
- 状态更新器
- Recall 策略
- 卡片迁移器
- 前端视图模块

并且新模块不应要求重写整个系统。

### 1.8 可持续演进

系统应能从：

```text
单故事小说流水线
→ 多故事并行
→ 玩家可互动 RP
→ 角色自治
→ 沙盒模式
```

逐步扩展，而不是每扩一次就推翻前一版结构。

## 3. 设计总原则：什么必须做，什么不要做

### 3.1 必须做的设计

凡是满足以下任意一点，就值得做：

1. **能明显提升质量**
   - 例如：扩写后重审、状态一致性校验、角色独立认知边界。

2. **能明显降低 token / 时间浪费**
   - 例如：章节级失败隔离、局部补写、上下文缓存、快模型审查。

3. **能明显提升可迁移性**
   - 例如：卡片语义中间层、preset/profile、结构化 state schema。

4. **能明显提升可维护性**
   - 例如：事件驱动状态更新、artifact 明确化、workspace 独立。

5. **能明显提升 RP / 互动能力**
   - 例如：玩家输入解析、玩家可见状态与后台状态分离、角色独立反应器。

6. **能明显提升运维与恢复能力**
   - 例如：pause / resume、checkpoint、run journal、失败自动改道。

### 3.2 不应该做的设计

如果某设计只是：

- 看起来高级
- 增加很多文件和抽象层
- 不能直接提升质量或效率
- 不能被马上用来解决实际问题

那就不该进入当前阶段。

例如：

- 为了“多 Agent”而无意义增加十几个空壳 Agent。
- 为了“事件驱动”而在没有真实状态变化需求时引入复杂 reducer 框架。
- 为了“扩展性”而提前做一堆无人使用的 profile router。
- 为了“像酒馆”而提前复制酒馆整套前端，而没有先明确 NovelAgent 自己的后端边界。

## 4. 参考旧版《设计草案.md》后的核心目标扩展

旧版草案已归档到 [`docs/archive/legacy_design_2026-06-18/设计草案.md`](archive/legacy_design_2026-06-18/设计草案.md)。其中强调了三点：

1. **state.md 是实时状态核心**
2. **manifest.json 控制上下文按需注入**
3. **审查是质量核心，而不是 Writer 本身**

结合当前实现，未来版本必须扩展成：

### 4.1 状态层

当前只有：

- `state/state.md`
- `state/player_visible.md`

未来要进一步做到：

- state 结构化解析
- 状态推进有明确 schema
- 状态推进后自动审计
- RP 模式中，玩家只看到 `player_visible` 侧

### 4.2 上下文注入层

当前只有：

- `preset.yaml`
- `modules/*`
- `agents.yaml` 的 inputs

未来要进一步做到：

- `manifest.json` 不只是记录路径，而是成为**上下文路由表**
- 不同 Agent 看到不同文件集
- 角色 Sub-agent 只看到属于自己认知范围的上下文
- RP 模式下 GM / 玩家视角 / 角色视角的上下文严格分离

### 4.3 审查层

当前已经有：

- `outline_worldbook_guard`
- `outline_knowledge_guard`
- `character_guard`
- `continuity_guard`
- `style_detail_guard`

未来必须补上：

- 扩写后重审
- 修订后再审查
- 审查失败自动回流
- 审查报告结构化解析

这部分是系统效果能否稳定的关键，不是可选项。

## 5. 参考 `tavern2agent` 后，卡片迁移应该怎么做

`tavern2agent` 的核心启发是：

> **不要直接复制角色卡文字，要先抽取语义，再决定运行时。**

### 5.1 NovelAgent 应该迁入什么

必须保留：

- 角色卡中的人物设定
- 世界设定
- 行为规则
- 触发条件
- 关系信息
- 隐藏信息 / 可见信息边界
- 可变状态（任务、好感度、时间、经济等）
- prompt 组合思路

不必直接照搬：

- ST 前端 UI 补丁
- HTML 状态栏
- JSON patch 输出格式
- 宏运行时 hack
- COT 标签

### 5.2 为什么不能直接“卡片 → prompt”

如果直接把 ST 卡片拼成 prompt，会导致：

- 隐藏信息边界失效
- 可变状态没法维护
- 多角色设定难以按 agent 分发
- RP 时玩家输入无法进入真实状态系统
- 复杂卡片（任务、好感度、时间）无法落地

### 5.3 NovelAgent 应该加入的迁移链路

建议加入：

```text
酒馆卡
→ Card Semantic IR
→ Runtime Plan
→ NovelAgent Project Files
```

最小落地文件：

```text
data/card_ir.json
data/runtime_plan.json
```

#### `card_ir.json` 负责保存
- 角色基础资料
- 公开信息 / 隐藏信息
- 世界规则
- 变量与状态项
- 触发条件
- 关系图谱

#### `runtime_plan.json` 负责保存
- 该卡应走 novel 模式还是 rp 模式
- 是否需要 evented runtime
- 是否需要角色独立 agent
- 哪些状态需要落盘
- 哪些模块要挂载

### 5.4 什么时候该做“prompt-only”，什么时候该做“事件驱动”

参考 `tavern2agent` 的按复杂度分档思想：

#### 只做 prompt-only
适用于：
- 纯设定卡
- 几乎没有状态变化
- 只是人物写作风格迁移

#### 做事件驱动状态更新
适用于：
- 有任务、好感度、时间、经济等可变状态
- 有隐藏信息边界
- 有多 NPC / 多角色并行互动
- 要做 RP

NovelAgent 的最终目标包含 RP，所以**必须走事件驱动状态更新**，至少在 RP 模式里必须如此。

## 6. 前端目标与演进路线

### 6.1 前端定位

NovelAgent 的前端不应被设计成“先复制酒馆前端，再去找后端适配”。

正确定位是：

> **前端是操作层、展示层、调试层，不是真实状态计算层。**

前端应该做：
- 展示 story / state / archive / evaluation
- 接收玩家输入
- 展示 agent 流程进度与中间产物
- 管理卡片导入、preset、profile、模块挂载
- 作为 RP 的输入输出界面

前端不应该做：
- 自己组装最终 prompt
- 自己维护 canonical state
- 自己推进事件状态
- 自己决定 Agent 调度

### 6.2 为什么前端必须排在卡片迁移之前

因为如果没有最小前端，卡片迁移只能产出一堆文件，但用户：

- 看不到迁移后的状态层结构
- 无法检查 card IR
- 无法选择 runtime plan
- 无法验证玩家可见信息和后台信息的分离
- 无法顺畅进入 RP 交互

所以正确顺序应是：

```text
先补最小前端交互层
再做酒馆卡迁移
```

### 6.3 第一阶段前端：最小 UI

这是**必须做且复杂度最低**的一层。

功能只包含：

1. **Story 列表页**
   - 浏览 `stories/`
   - 创建新 story
   - 进入 story

2. **Story 总览页**
   - 当前 premise / outline / state 摘要
   - 当前 open threads
   - 最新章节列表
   - 最新评估结果

3. **章节查看页**
   - 查看 `novels/chapter_xx.txt`
   - 查看对应 archive 内容
   - 查看审查报告

4. **RP 输入页（最小版）**
   - 玩家输入框
   - 返回 GM 旁白 / 角色反应
   - 查看 `player_visible.md`

5. **日志与调试页**
   - 当前 pipeline 步骤
   - 上一次失败在哪一步
   - 当前使用哪个模型 tier

#### 第一阶段前端原则

- 不做复杂组件化酒馆 UI
- 不复制 ST 面板系统
- 不做富文本状态栏
- 不做复杂角色管理器
- 只做最小必要交互

### 6.4 第二阶段前端：RP 专用交互界面

当最小 UI 稳定后，再补：

- 对话窗
- 玩家输入历史
- 旁白 / 角色响应分区
- player_visible 侧边栏
- 当前目标 / 关系 / 线索面板
- 场景内行动建议（可选）

这一阶段的目的是：

> 让玩家能真正使用 NovelAgent 作为互动系统，而不只是看它生成小说。

### 6.5 第三阶段前端：卡片迁移管理页

当最小前端和 RP 基础都稳定后，再加入：

1. 导入 ST 角色卡（PNG / WEBP / JSON）
2. 展示解析结果
3. 展示 `card_ir.json`
4. 展示 `runtime_plan.json`
5. 允许用户确认：
   - prompt-only
   - novel mode
   - rp mode
6. 一键生成 story workspace

这一步必须放在前端，因为它本质上是：

- 半自动导入
- 半人工确认
- 需要可视化比较与校对

### 6.6 前端配置页目标

既然目标是**所有 prompt 可配置、最终同步前端**，那么前端必须提供配置页，而且这不是“可选锦上添花”，而是高可配置性的实际落点。

前端配置页至少要覆盖：

1. **Prompt 配置**
   - 启用 / 禁用哪些 modules
   - 调整 module 顺序
   - 给 story / profile / agent 绑定不同 preset
   - 查看最终 prompt assembly 预览（只读）

2. **Agent 配置**
   - 启用 / 禁用某个 Agent
   - 替换某个 Agent 的 prompt
   - 调整该 Agent 的模型 tier
   - 查看该 Agent 的输入 / 输出 artifact

3. **Pipeline 配置**
   - 启用 / 禁用步骤
   - 调整步骤顺序
   - 是否并行某些 guard
   - 失败时是否允许降级 / 跳过 / 重试

4. **运行时配置**
   - 重试次数
   - 超时时间
   - backoff 策略
   - cache 开关
   - 章节长度目标
   - 是否自动扩写
   - 是否扩写后重审

5. **RP 配置**
   - 玩家输入解析模式
   - 角色响应模式
   - 可见状态显示策略
   - narrator / GM 风格模块

前端配置页必须遵循的原则：

- **前端只改配置文件，不直接改 runtime state**。
- **所有前端改动都必须映射到明确文件**（如 preset、profile、story config、pipeline config）。
- **前端不能成为新的配置真相源**，文件仍然是唯一真相源。

### 6.7 前端与后端边界

最终必须明确：

| 项目 | 后端 | 前端 |
|------|------|------|
| prompt 组装 | ✅ | ❌ |
| canonical state | ✅ | ❌ |
| event 处理 | ✅ | ❌ |
| 玩家输入采集 | ❌ | ✅ |
| 章节/归档查看 | ❌ | ✅ |
| story 管理 | ✅（文件） | ✅（操作） |
| 卡片迁移解析 | ✅ | ✅（展示/确认） |
| 配置修改 | ✅（落盘） | ✅（编辑界面） |

### 6.8 前端演进路线

```text
CLI
→ 最小 Web UI
→ 配置页
→ RP 专用交互界面
→ 卡片迁移管理页
→ 高级调试 / 审计视图
```

这个顺序是必要的，因为它兼顾：

- 最小复杂度
- 最快验证玩家交互目标
- 为卡片迁移提供真正可用的落点
- 为“所有 prompt 可配置”提供真实 UI 承接

## 7. 高可配置性与高可插拔性

### 7.1 高可配置性的定义

NovelAgent 的“高可配置性”不是指让用户到处改 Python 代码，而是：

> **系统的主要行为都能通过文件配置与前端配置页调整，而无需修改核心编排代码。**

必须配置化的对象：

1. Prompt modules
2. Preset
3. Profile
4. Agent 列表
5. Pipeline 步骤与顺序
6. 模型 tier 分配
7. 重试 / backoff / timeout
8. Recall 策略
9. 扩写策略
10. RP 模式策略

### 7.2 高可插拔性的定义

NovelAgent 的“高可插拔性”是指：

> **新增一个模块、Agent、pipeline 步骤、迁移器或前端视图，不需要重写系统，只需要按约定接入。**

必须支持插拔的对象：

- Prompt modules
- Agents
- Pipeline steps
- Recall backend
- State updater / reducer
- Card importer
- Frontend views

### 7.3 必要的配置文件层级

未来建议形成以下层级：

```text
system config      全局默认配置
profile config     某类运行风格配置
story config       某个故事独有配置
run override       单次运行临时覆盖
```

优先级：

```text
global < profile < story < run override
```

这样既能共享默认值，也能给单个故事做深度定制。

### 7.4 配置化的最小实现顺序

第一步先做：

- retry / timeout / backoff 配置化
- auto-expand / auto-review 开关配置化
- prompt module 启停配置化
- agent tier 配置化

第二步再做：

- pipeline 顺序配置化
- RP 策略配置化
- card import runtime plan 配置化

## 8. 环境隔离、上下文隔离、可恢复、可暂停

### 8.1 环境隔离

环境隔离的目标不是“虚拟化一切”，而是保证：

- 不同故事互不污染
- 不同运行模式互不污染
- 不同卡片导入结果互不污染

因此必须做到：

1. **每个 story 独立 workspace**
   - `stories/<story>/...`
2. **不同故事有独立的**
   - `lore/`
   - `state/`
   - `memory/`
   - `archive/`
   - `novels/`
   - `evaluation/`
3. **初始化不带脏数据**
4. **迁移卡片时默认生成新 story root**

### 8.2 上下文隔离

上下文隔离是多 Agent / RP 成败的关键。

必须做到：

1. 不同 Agent 读取不同文件集
2. 玩家视角不能看到 hidden state
3. 角色 Sub-agent 只能读取与自己认知相关的内容
4. 审查 Agent 不应写正文
5. Writer 不应直接写 state

因此未来必须把：

- `manifest.json`
- `agents.yaml`
- `profile`
- `runtime_plan`

统一成真正的上下文路由系统。

### 8.3 可恢复

可恢复不是“失败后重新跑”，而是：

> **在已归档的中间产物基础上，从失败点继续。**

必须支持：

1. 章节级 resume
2. 扩写失败 resume
3. 审查失败 resume
4. RP session resume
5. 卡片迁移半程失败 resume

要达成这一点，必须补：

- `run journal`
- step-level status
- artifact completeness 标记
- degraded 标记
- checkpoint 文件

### 8.4 可暂停

可暂停对 RP 与长篇生成都必要。

暂停后必须保留：

- 当前 state
- 当前 player_visible
- 当前 chapter scene cursor
- 当前 open threads
- 当前 recall index
- 当前 artifact 进度

恢复时应能：

- 从暂停前的 pipeline step 恢复
- 从暂停前的 RP turn 恢复
- 不重复消耗已完成步骤的 token

### 8.5 这些能力为什么必要

因为如果没有环境隔离、上下文隔离、可恢复、可暂停：

- 多 story 会互相污染
- RP 时会泄露后台真相
- 一次失败要重跑整章整本
- token 花费不可控
- 前端交互无法稳定承接长时间会话

所以这些不是“以后再说”的锦上添花，而是达到目标所必须的基础设施。

## 9. 测试原则：最小化 token 花费

这是本项目必须新增的总原则。

> **严格只在最终测试阶段引入真实 LLM，不允许把“调试代码 / 对齐 contract / 修 YAML / 修路径 / 修状态推进”这些工程问题放到真实模型上反复试错。**

### 9.1 原则解释

任何能靠以下方式验证的问题，都不应该先打真实模型：

- 静态检查
- mock runner
- schema 校验
- 文件结构审计
- 归档检查
- pipeline dry run
- contract 校验
- 局部 deterministic 测试

只有当以下条件同时成立时，才允许进入真实 LLM 测试：

1. 文件路径正确
2. pipeline step 顺序正确
3. artifacts 路由正确
4. validator contract 正确
5. 失败恢复逻辑正确
6. 归档逻辑正确
7. mock / stub 流程已通过

### 9.2 测试分层

#### 第 0 层：静态与结构验证

- Python compile
- YAML / JSON 可读性
- 路径映射
- preset / module 存在性
- agent config 完整性

#### 第 1 层：Mock Runner 验证

验证：
- 步骤是否按顺序执行
- artifact 是否写到正确位置
- archive 是否生成
- story workspace 是否隔离

#### 第 2 层：局部 deterministic 测试

验证：
- 状态推进函数
- summary/index 更新逻辑
- import-card 转换逻辑
- runtime plan 选择逻辑
- retry / backoff 配置逻辑
- pause / resume 状态恢复逻辑

#### 第 3 层：最小真实 LLM smoke test

只打：
- 一个最小生成步骤
- 一个最小审查步骤
- 一个最小评估步骤

目的只是证明链路可用，不是追求成品。

#### 第 4 层：最终真实场景测试

只有前 3 层都通过后，才允许：

- 真实章节生成
- 真实 RP 对话测试
- 真实卡片迁移整链测试

### 9.3 为什么这条原则是必要的

因为本项目当前的很多失败，本质上都不是模型问题，而是：

- contract 错位
- 路径错位
- 归档污染
- 状态推进逻辑错误
- 脏工作区残留

这些问题如果用真实 LLM 去反复测，只会：

- 白白烧 token
- 浪费时间
- 让错误定位更困难
- 掩盖工程问题本身

所以：

> **真实 LLM 不是调试器，只是最终验收工具。**

这一条必须成为 NovelAgent 的强约束。

## 10. 未来目标结构：从小说流水线到可互动 RP 系统

最终应分成四层：

### 10.1 生成层（Novel Mode）

职责：
- 题材初始化
- 章节规划
- 正文生成
- 审查闭环
- 记忆维护
- 成品输出

### 10.2 状态层（Evented Runtime）

职责：
- 角色、世界、任务、好感度、时间等状态的变更
- 事件记录
- reducer 风格更新
- 审计与回滚

### 10.3 互动层（RP Mode）

职责：
- 玩家输入解析
- 视角受限状态显示
- GM 响应
- 角色回应
- 事件落盘

### 10.4 前端层（UI / Migration / Debug）

职责：
- 展示 story / state / archive / evaluation
- 接收玩家输入
- 展示 agent 步骤与失败位置
- 承接卡片迁移结果与 runtime 选择
- 承接所有 prompt / pipeline / agent 的配置页面

这四层里：

- **生成层**已经有雏形
- **状态层**目前只有文件，没有事件系统
- **互动层**几乎还没开始
- **前端层**当前还未正式纳入实现，只在目标中出现

## 14. 一句话结论

NovelAgent 现在已经证明：

> **文件驱动 + 多 Agent 串行流水线 + 模块化 prompt + 章节级归档** 这条路是可行的。

但要真正达到：

```text
玩家能互动
成本可控
效果稳定
可迁移酒馆卡
高可配置
高可插拔
环境隔离
上下文隔离
可恢复可暂停
```

还必须补上五大能力层：

1. **闭环质量控制层**（重审、返工、状态审计）
2. **事件驱动状态层**（RP 与可变世界的基础）
3. **前端交互承接层**（玩家使用与卡片导入的必要落点）
4. **卡片语义迁移层**（ST / 酒馆生态接入）
5. **配置与恢复层**（高可配置、高可插拔、pause / resume、环境与上下文隔离）

在这五层中，当前最该优先做的是：

> **先把闭环补齐，再做最小前端与配置页，再做 RP，再做酒馆卡迁移。**

否则系统会在“能跑但不稳”的状态上不断堆复杂度，最终既不省 token，也不真正好用。
