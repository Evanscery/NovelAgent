自从入坑 Agent 后，我的酒馆已经吃灰很久了。逛了一圈社区，发现目前似乎还比较缺全流程的详细经验分享。今天就抛砖引玉，聊聊我自己的多 Agent 工作流和处理方式。

我的核心需求比较严苛，成品基本是对标严谨的小说创作：

1. **叙事连贯**：不失忆，上下文高度一致。
2. **逻辑严密**：没有设定硬伤，细节经得起推敲。
3. **角色生动**：拒绝 OOC，做好严格的认知隔离。
4. **文风优质**：正文坚决不要 AI 八股味。

为了达到这个标准，我把**「审查」**做成了整个工作流的核心环节，甚至专门安排了 4 个 Critic 作为独立的 Sub-agent 来审稿。

这里以 Pi 作为例子。

---

### 💡 核心设计思路

1. **`state.md`（实时状态）**：
类似于酒馆的 MVU 或 EJS（没错，EJS 也可以放这里）。建议把人设中最核心的部分一起写进 `state`，作为后续所有打工 Agent 的基底参考。
2. **`manifest.json`（控制上下文按需注入）**：
每个 Agent 分工不同，比如写实审查不需要看人设，但角色审查和写手必看。为了避免 GM 输出污染上下文且实现认知隔离（给独立角色用），我写了个扩展自动读取 `manifest.json` 里的文件路径。这样启动时既不用挨个手动读取文件，又能把分好类的设定精准注入给对应的 Agent。
3. **颗粒度递进（周大纲 → 轮次细纲 → 草稿 → 成品）**：
这个节奏刚刚好。周级大纲控伏笔和节奏，轮次细纲保初审逻辑，草稿出来后再由细节审查做精修。

### ⚙️ 基本架构：GM 与 打工人们

> **GM（主控）**：负责项目管理。推 pipeline、写周级大纲、维护后台（更新 state / manifest / 记忆 / 清理临时文件）。
> **Sub-agent（打工人）**：按需干活。给它们开放 read / bash 权限，遇到不懂的它们会自己去翻设定求证。

---

### 🚀 完整工作流 (Pipeline)

1. **抓取现状**：从 `state.md` 获取当前截面（时间、人物状态、事件进度）。
2. **对齐大纲**：读取周级大纲 `outline.md`，确认当前叙事状态（伏笔、待办事件、叙事基调）。
3. **提取设定**：从知识库翻阅当前场景的关联设定。
*(建议：提前归类好设定并建个 `packs.md` 索引速查表，方便用 cat 一次性读全)*
4. **配置清单**：分发任务前，更新一遍 `manifest.json`。
5. **记忆召回**：Recall 翻日志和原文，检索当前场景的相关历史记忆。
6. **编写细纲**：GM 亲自写；遇到关键剧情，就并行分发给 2-5 个 **Brainstormer** （脑暴）提供不同视角的参考。
7. **细纲定稿**：敲定细纲，并更新最终版 manifest。此时 GM 知道的内容是最全面的（recall 报告、自己又确认了细纲的方向），因此需要再更新一次。
8. **细纲审查**：并行分发给 **Critic-Realism**（写实/逻辑）与 **Critic-Character**（防 OOC）。
9. **起草正文**：根据审查报告修改后，交接给 **Writer** 拿到正文草稿 `draft.md`。
*(建议这里设为异步，后续如果发现严重 Bug，能随时唤醒 Writer 返工)*
10. **草稿审查**：先过一遍 **Critic-Detail**（抠物理动作细节），修改后再过 **Critic-Style**（杀八股），最终拿到成品。
11. **归档清理**：按照正文更新 `state.md`，归档草稿，更新记忆和日志，清理临时文件。
12. **收尾呈现**：将成品展示给玩家，并给出下一步行动选项（GM 也可按照大纲在这里做一定的剧情引导）。

---

### 🔍 核心模块解析

**1. 审查模块 (Critic) —— 极度关键**
强烈建议：**千万别跳过审查，也别让模型自己审自己**（它根本看不出自己的问题）。

* **Critic-Realism**：查逻辑、合理性、上下文一致性（比如早上如果是开车来上班，晚上就别走路回家）。如果是魔幻世界观，就让它查“是否忠实于规则机制”。
* **Critic-Character**：防 OOC。
* **Critic-Detail**：专抓物理细节（动作连贯性、手部状态、体位姿势，我平时最讨厌那种手上拿着东西又推一下眼镜的细节，被抓出来真的很出戏）。
* **Critic-Style**：杀八股，也能一定程度上特化文风。
* *实际感受*：除了 Character 审查在前期设定好时不易崩之外（基本都是通过，但是其实也能给出建议，优化一些细节，丰富角色活人感），剩下三个 Critic 对成品的质量有着决定性的影响。

**2. 召回模块 (Recall)**
上下文太长时触发，也可以直接由 GM 取代。Agent 跑卡与酒馆不同的一点是，**最好做到历史正文全归档**。别怕麻烦，效果拔群。

**3. 创作模块 (Creation)**
Writer 在工作时，如果需要多种文风，或者如果平时玩NSFW，建议把各种文风和NSFW封装成独立的 Skill，方便随时调用。

### 💡 进阶玩法与优化建议

* **玩家审查机制（人机协同）**：
我曾嫌弃四个审查太慢，做了个直接把细纲扔给玩家批阅的 Quick 模式。结论是：极度费脑，而且逐个挑毛病其实比机器审还慢。
**最佳实践**：保留 Sub-agent 初审，玩家只负责最后的终审。
* **记忆系统推荐**：
社区有很多开箱即用的项目。独立角色我用 `nocturne`，工作流则用传统的日志系统（类似酒馆的：每轮400字客观小结 + 索引 + 归档的正文）。这种方式又轻量又准，Brainstormer 查重或 Realism 查连贯性时，找起来比复杂的记忆系统更方便。
* **独立角色（沙盒模式的雏形）**：
为了彻底解决 OOC，其实可以直接给每个角色挂一个独立的 Sub-agent 和记忆系统。让它们自己决定该做什么，甚至直接对草稿提出批评建议。如果是群像剧，用这招替代 Critic-Character 简直绝杀。这其实已经脱离了 Pipeline 变成了沙盒模式，非常好玩，后续我会单开一贴细说。
* **基建工具化**：
把常用的功能统统变成工具调用。比如玩家审稿，只需封装一个 `review({path:"...", label:"细纲"})`；呈现正文就写个轻量的 HTML 转化器 `reader({path:"..."})`。这样可以节省大量 token，不让 GM 浪费算力去反复输出相同的内容。
